# CritterCab v2: dual-evaluation framing

**Decision owner:** Erik Shafer. **Date:** 2026-10-05. **Method:** the CritterBids `dual-evaluation` skill. This framing is handed identically to two independent evaluators. It states the question, the options, and the facts. It does not state a preference.

## The question

Should CritterCab become a "v2", and if so in what form? "v2" here means what the CritterCommerce to CritterShop to CritterSupply to CritterMart lineage meant by it: a deliberate new version that acts on lessons learned, condenses and folds bounded contexts, simplifies logic that got out of hand, and drops what did not earn its keep. It is not a fresh coat of paint, and a rewrite is not assumed to be the answer.

## The options

1. **v2 as a new repository.** A fresh repo (name open) seeded from the parts of v1 that survive; v1 archived read-only on GitHub.
2. **v2 in place.** The same repository, same issue and PR history, with a declared v2 boundary (a tag, a vision v1.0, folded docs) and v1 artifacts retired or archived under a `v1/` or `archive/` path.
3. **Remaster the conventions and continue.** No version boundary. Fix the drift, fold the BC list, adopt the portfolio's Event Modeling decision, retire what is dead, and keep building from the 2026-07-25 handoff.
4. **Continue as is.** Take the handoff's own next step (Driver Profile workshop, or a `tidy: skills` session) with no structural change.

A hybrid is a legitimate recommendation if argued.

## What kind of answer is wanted

A recommendation with reasoning, numbered evaluation points, explicit treatment of the options you reject, references into the lived repo (file paths), and the costs of your recommendation. The evaluation must stand alone. Where it bears on the call, answer: whether "v2" is meaningful at 2 of 11 BCs or the design corpus is the asset and v2 is really a reset of conventions; which BCs survive, fold, or drop and what the service count becomes; what v1 got wrong that v2 must not repeat and what v1 got right that v2 must keep; what happens to the old repo; which tech stays, goes, or is added; how v2 does Event Modeling from the first commit under the portfolio decision below and what happens to the six existing workshops; and what the first slice of v2 is.

## Constraints that are not up for argument

The portfolio decided on 2026-10-05 (record: the Project's `em-source-of-truth-evaluation-comparison.md` §7): the Event Model's authored surface in every Critter repo is a committed curated `*.emodel.yaml` (JasperFx's declared rung); the EventModelers.AI canvas is the modelling room for new chapters and an import path, never the record; no build-kit loop and no asserted status in any file; Gherkin via Bobcat is the executable layer (scaffold for new slices, `[BobcatSlice]` binding for existing tests); the rung derived from the running app is always on and never authored; markdown workshops are the minutes of the conversation. The portfolio lens ranks Event Modeling practice first and JasperFx product showcase second. No talk is committed and nothing needs to be reachable at a URL. ADRs are not written in this session. No code changes come out of this session. Vocabulary: keep Dymitruk's Command / View / Automation / Translation, Dilger's State Change / State View / Automation / Translation, and JasperFx's descriptor terms distinct; "source" means an `IEventModelDefinitionSource` producer, "surface" means what humans author.

The Polecat placement question is parked for the CritterCab session with the argument already made (Project baseline §8): lean yes, CritterCab should make room for Polecat because CritterBids' failure (two stores claiming the main store in one host) cannot happen under service-per-BC; choice (a) the business-events half starting with Driver Profile versus (b) Payments-first per the vision; Dispatch and Telemetry stay on Marten either way; Fisher does not belong in CritterCab. You may take a position on (a) versus (b) and on whether Polecat belongs in v2's first arc; you may not re-argue the Event Model authored-surface decision.

## Lessons the artifacts record (condensed; the evaluation doc will cite them in full)

Domain: Dispatch owns its geo projection as a multi-transport join (ADR-018, W006 grill R1/R2); Telemetry is stream-processing, never event-sourced, availability-agnostic (W006 grill R4/R8); selection optimises recall and acceptance enforces correctness (R3); "LWW per driver per side" means two clocks and one revision column cannot serve both (retro 009); do not fabricate availability to keep a demo alive (retro 009); workshop vocabulary wins over framework naming (retros 003, decisions 001); DS pays off for vocabulary-rich multi-actor BCs and not for machine-to-machine ones (W003 retro, log entry 005); translation-dominant BCs need an inline foreign-key index (W005 retro); the modeling-shape taxonomy discriminates on "is there a load-bearing invariant" (W005 retro).

Methodology: source-of-truth precedence is working code, then retro, then external docs (skills-tidy retros); verify-before-wiring earns its cost by disconfirming the prompt's own hypotheses (retros 006 to 009); run source verification at prompt authoring, not session start (retro 008); source verification and skill-auditor Phase 1 catch disjoint error classes, both needed in that order (008, 009); four review passes found four disjoint classes and the two-axis code review caught the worst defect after three clean passes (008, 009); gates answer at the question's implicit cardinality and check signatures not units (009); escalate under-specification as a fork with a recommendation; a skill's written "not yet" is a decision (007, 008); grill-with-docs front-loads boundary calls and the first question carries disproportionate leverage (W005 retro, frontend-unpark); the per-unit explicit-lean sign-off is the solo-plus-AI primitive that worked (W003, context-map); lean-confirmation mode is a risk, zero of ~20 leans redirected in W003; the spec-delta loop held, including the honest null case; the narrative layer can be skipped for headless BCs when recorded; prove a regression test fails (009); reference repos are live, log the HEAD of each verified source (phase-4, 006).
