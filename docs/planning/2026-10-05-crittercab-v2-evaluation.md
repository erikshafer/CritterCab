# CritterCab v2 evaluation: should there be one, and what would it entail?

**Written:** 2026-10-05 · **Branch:** `main` @ `4d8bde4` (clean; nothing changed in `src/`, nothing committed) · **Session:** the design-or-tidy return the 2026-07-25 handoff demanded, run as a planning session in the "Critter Projects by Erik" Project · **Status:** evaluation complete; **Decision section blank, awaiting Erik**

This document answers the session prompt "Should there be a CritterCab v2, and what would it entail?" in four passes (lessons, inventory, v2 shape, repo call), then answers the seven questions the prompt names, lists the risks of the recommendation and what could not be verified, and leaves the decision to the owner. The contested call (rewrite versus remaster versus continue) was run through the CritterBids `dual-evaluation` skill; its three files sit in `docs/research/` (framing, two independent evaluations, comparison) and this document cites the comparison rather than restating it.

"v2" is used throughout in the sense the CritterCommerce to CritterShop to CritterSupply to CritterMart lineage gave it: a deliberate new version that acts on lessons learned, condenses and folds bounded contexts, simplifies what got out of hand, and drops what did not earn its keep. A rewrite was not assumed.

**Short answer.** Yes, there should be a v2, and it should be declared in place: same repository, same history, a tag closing v1 at `4d8bde4`, a vision v1.0 that cuts the bounded-context inventory from eleven to five deployables, a declared Event Model per service as the authored surface, and a first arc that builds Driver Profile on Polecat so the existing cross-service flow gains its second feeder. The code is not rewritten because there is almost nothing to rewrite; what gets versioned is what the repository claims about itself. Both independent evaluations reached this by different routes (comparison §1.1, §1.2). The residual calls are the owner's and are listed in §7 and §10.

Portfolio decisions honoured and not re-argued here: the curated `*.emodel.yaml` is the authored surface; the EventModelers.AI canvas is the modelling room and an import path, never the record; no build-kit loop, no asserted status; Gherkin via Bobcat is the executable layer; the derived rung from the running app is always on and never authored; markdown workshops are the minutes. "Source" means an `IEventModelDefinitionSource` producer; "surface" means what humans author. Dymitruk's Command / View / Automation / Translation, Dilger's State Change / State View / Automation / Translation and JasperFx's descriptor terms are kept distinct.

## Pass 1: what v1 actually taught

Every lesson below cites the artifact that supports it. Lessons the artifacts do not support were not invented; where a lesson recurs, the recurring artifacts are named. The retrospectives, the methodology log, the DEBT ledger, the planning handoffs and the ride-sharing research were the inputs.

### 1.1 About the ride-sharing domain

The one load-bearing domain decision v1 made and proved in code is that Dispatch owns its candidate view as a join of two flow shapes on two transports. The W006 grill resolutions say it plainly: "`NearbyAvailableDrivers` is a **Dispatch-owned local projection**, not a Telemetry-owned queryable index" and "the view is a **multi-transport projection**: Kafka (geo) + ASB (availability) folding into one Dispatch-local view" (`docs/planning/2026-06-25-w006-telemetry-grill-resolutions.md`, R1 and R2; committed as ADR-018). The same grill settled that Telemetry is "never event-sourced (per-ping-per-driver would detonate any event store)" (R4), that "'Active' = **actively pinging**, never *available*" and Telemetry "**never consumes Driver Profile**" (R8), and that "Selection optimizes for *recall* from a local view; acceptance enforces *correctness* (exactly-one assignment)" (R3).

Implementation then taught two things the model had not said. First, "LWW per driver per side" means two clocks: "One column cannot serve both when there are two clocks. The concrete failure: a driver goes Offline at 12:00:05, a heartbeat position stamped 12:00:07 arrives first and raises the revision, and the Offline write is then discarded by `where mt_version < ?` — **leaving an offline driver dispatchable, with no error anywhere.**" (`docs/retrospectives/implementations/009-dispatch-w006-slice-5-nearby-available-drivers.md`). Second, do not fabricate what the model has no source for: "The tempting move — default a location-only driver to `Available`/`STANDARD` so the demo works end to end — would have had Dispatch fabricate a capability claim at the point of query, invisibly. Excluding instead makes the system honestly report that it cannot dispatch yet" (same retro). That is why a real run today ends in `NoCandidatesAvailable`, and why the first slice of v2 is already chosen (§3.9).

Vocabulary lessons recur across three artifacts: "Where the workshop and skill disagreed (e.g., `Location` vs `GeoLocation`, `lat`/`lon` vs `latitude`/`longitude`), the workshop was followed. The workshop carries the domain reasoning; the skill carries the mechanical convention." (`docs/retrospectives/decisions/001-protobuf-ride-assigned.md`; also `implementations/003`, `decisions/003`). The modeling-shape taxonomy v1 arrived at is the durable domain output of the workshops: "The discriminator is ADR-012's own question: *is there a load-bearing invariant?* None → translation-dominant (Identity); one fitting a single stream → aggregate-per-invariant (W001/W002); coordination-dominated → Process Manager (W004)" (`docs/retrospectives/workshops/005-identity-event-modeling.md`), with W006 adding stream-processing as a fourth shape. Translation-dominant BCs "need an inline foreign-key index (`ProviderSubjectIndex` / `BackgroundCheckVendorCaseIndex`)" (same retro; W004 and W005).

### 1.2 About the methodology

Domain Storytelling earns its place for vocabulary-rich BCs and not for machine-to-machine ones. Methodology log entry 005 (`docs/research/methodology-log.md`) records that W004 "had zero mid-walk vocabulary scrambles" after W003 while W002 "required three iterations plus a mid-sidebar web-research turn", and names the confound honestly: "Much of W004's smoothness traces to the prompt's four `grill-with-docs` resolutions". Entry 006 separates the axes: "**Domain Storytelling** surfaces *vocabulary divergence* ... **Grill-with-docs** surfaces *strategic-design boundary calls*". The W003 retro adds the caveat that "DS value would likely be *lower* for narrow, mechanical BCs (e.g., a pure projection-fed Telemetry BC)" (`docs/retrospectives/workshops/003-onboarding-domain-storytelling.md`, Q5).

The grill did the heavy lifting, which is both a strength and a warning. W005's retro: "**Almost nothing — and that is the finding.** The grill did the hard work; the workshop was light." The W003 retro records the risk on the other side: "the user did not redirect any of the ~20 leans Claude proposed across the session. That is consistent with the leans being calibrated well ... but is also consistent with the user operating in lean-confirmation rather than independent-domain-expert mode". Evaluation A names this as the design conversation being "mostly a record of ratification" (comparison §3). The per-unit explicit-lean sign-off is nevertheless the primitive that made solo-plus-AI work: "capture batch → 1–3 focused questions → each with a lean → user confirms / redirects / escalates — is the methodology innovation that made the solo + AI adaptation work" (W003 retro; `docs/retrospectives/context-map-foundation.md` generalises it to "any artifact with N independent decisions").

Verification before wiring earns its cost only by disconfirming. "A verification pass that only ever confirms is not doing its job; this one disconfirmed twice (gates 5 and 8a) and closed the rest" and "The verification pass earns its cost specifically by being able to contradict its author" (`docs/retrospectives/implementations/007-telemetry-slices-4-and-2-transport.md`). Timing matters: "**Run the source-verification pass during prompt authoring, not at session start.** The gap it found here changed a signed-off fork." (`implementations/008`). The passes are not redundant: "This prompt was thoroughly gate-verified and still had four convention-level errors the Phase 1 auditor caught, including a missing governing skill. Both passes, in that order." (`implementations/008`); "**Four review passes found four disjoint classes of problem, and none was redundant.**" (same); and the worst defect of the whole project was found last: "`code-review`'s two-axis form found it, and **both axes found it independently**" (`implementations/009`). The limits are recorded too: "when a source-verification gate asks 'what is the best API for X,' the answer is scoped to the question's implicit cardinality" and "Source verification as currently practised checks signatures. It does not check units" (`implementations/009`).

Under-specification is escalated as a fork with a recommendation, never a silent default: "Three forks were raised this session; all three took the recommendation, and one produced a better model than either source doc" (`implementations/007`); "**A skill that says 'not yet' is a decision, not a silence.**" (`implementations/008`); and the test for whether to ask is "would the alternative change the persisted shape of the code (return types, DI records, public APIs)?" (`implementations/004`). Prompt-supplied code is guidance: "design-decision snippets in prompts are guidance, not specifications, and the implementer is responsible for the executable shape" (`implementations/004`).

The spec-delta loop held across substantive and null cases: "Three single-bullet entries in the prompt's `## Spec delta` translated directly into three checkbox-style confirmations below. No structural friction" (`implementations/003`); "name the no-delta explicitly with reason, rather than skip the section or confabulate" (`docs/retrospectives/housekeeping-delete-may-15-handoff.md`). The narrative layer can be skipped when recorded: "Future headless / machine-to-machine BCs run the same empirical test and record the skip in the same table" (`docs/retrospectives/telemetry-narrative-layer-decision.md`). Tests must be proven to fail: "**The first version of the 'regression' test was a false witness**, and a five-minute revert-and-rerun was what distinguished it from a real one" (`implementations/009`); "**The pinning tests were designed to fail, not to pass.**" (`implementations/007`). Reference repos are live: "verifier verdicts should always carry the checked-out version" (`implementations/006`; `skills-foundation-phase-4`).

Two method gaps the artifacts show rather than state, surfaced by Evaluation A and verified: there is exactly one wireframe in the whole corpus (W001 §5.1), and Dymitruk's information-completeness check is never named or performed in any workshop or in the `event-modeling` skill; W001 §5.2's Reads-list inconsistency, "carried from retro 004" and still open (`implementations/005`), is the kind of defect that check exists to catch.

### 1.3 About the stack

The expensive lessons were library facts the skills had guessed wrong. "`SingleStreamProjection` is in `Marten.Events.Aggregation`, not `Marten.Events.Projections` ... the namespaces are counterintuitive" (`implementations/002`); "**The `partial` requirement is the headline Marten 8→9 migration trap for this codebase.**" (`docs/retrospectives/fix-marten9-projection-source-gen.md`). "Wolverine's handler-discovery failures land as warnings, not exceptions" (`implementations/003`) and automations "require **two** independent registration steps (`UseFastEventForwarding` *and* `CustomizeHandlerDiscovery(...WithNameSuffix("Automation"))`), not the one the DEBT row named" (`docs/retrospectives/skills-tidy-wolverine-marten-automation.md`). The prompt's hypothesis "that Wolverine has a recurring-message primitive ... was **wrong on both counts**" (`implementations/007`); the idiom is a `BackgroundService` with `IServiceScopeFactory` because `IMessageBus` is scoped (`docs/skills/DEBT.md`).

gRPC client-streaming was a three-month forward-constraint that a version bump closed: "The client-streaming shape — three months of forward-constraint, two skills' worth of workaround documentation, a standing entry in every handoff — took an empty one-line stub and a handler that imports nothing from `Grpc.*`" and "**Middleware does not weave for client-streaming**, so per-ping validation *must* live in the handler" (`implementations/007`). Kafka ordering is configuration, not statement order: "the naive implementation — write the two calls in the order §6.3 specifies — would have produced a system where publish-first is true in statement order only" (`implementations/008`). The cold-start offset is a production decision: "`BeginAtEarliest()` would have turned all four tests green in one line ... and would have committed the service to replaying its entire retained topic on every fresh deploy" (`implementations/009`). Marten revision types matter by "a factor of about 800" (`ILongVersioned` versus `IRevisioned`, `implementations/009`); "**`HardDeleteWhere` vs `DeleteWhere` is a domain decision wearing an API costume.**" (`implementations/007`). H3 has a radians trap and a k-ring divisor trap: "Two plausible numbers a factor apart, where the factor *is* the bug" (`implementations/009`).

Build and CI lessons recur across five artifacts. "**File-based program + repo-wide CPM is a standing trap.**" (`docs/retrospectives/aspire-reconcile-and-port-band.md`); "The apphost is a **file-based app with no `.csproj`**, so it falls through a guard that already exists" (`implementations/007`); "**Still true and still unaddressed:** CI cannot build `apphost.cs`." (`implementations/009`). Testcontainers: the wrong image "exited 1 with `No 'meta.properties' found`" (`implementations/008`); "**'It failed in code I didn't touch' is evidence about *load*, not innocence.** The blast radius of a new test fixture is the whole CI job" (`implementations/009`); the pre-pull list exists and "nothing enforces it" (handoff 2026-07-25). FluentValidation in Wolverine.HTTP is a two-call wiring and "the smoke test's green gave false confidence about a validation path it never touches" (`implementations/006`). `buf` lint against ubiquitous-language names is "a user decision, surfaced explicitly — do not silently conform ... or silently except" (`decisions/003`); `buf` was never installed locally (`implementations/003`). Speculative seams paid off: "**The seam-first discipline paid off twice in one session.** ... Both were speculative when built. Both were right." (`implementations/009`).

### 1.4 About maintaining the repo

Design ran far ahead of code and the repo said so about itself: "**The showcase premise is ~0% demonstrated.** gRPC, Kafka, and ASB — the entire reason CritterCab exists — are declared as packages and modeled richly in workshops, but **not one is wired in a single line of `.cs`**." (`docs/planning/2026-06-25-state-of-the-repo-transport-and-critterwatch.md`, written two months after the skills README had declared all five skill phases complete). Skills authored ahead of code contradicted each other and the APIs: "The `service-bootstrap` and `aspire` skills contradicted each other on connection-string handling" (`implementations/001`); "`wolverine-kafka/SKILL.md` was written well ahead of any implementation, and had independently arrived at two positions the shipping code contradicts" and "**The Aspire example in our own skill does not compile.**" (`implementations/008`); the `testing-integration` collection convention has "zero adherents" (`docs/skills/DEBT.md`).

Routing files decay while append-only artifacts stay honest: "Artifact files (workshops, narratives, ADRs) are append-only and stay correct by construction — they accumulate but rarely lie. Routing-layer files (`CLAUDE.md`, the per-layer READMEs) carry summary claims that decay silently as the project moves." (`docs/retrospectives/refresh-claude-md-and-encode-tidy-convention.md`). At HEAD the README, CLAUDE.md, AGENTS.md, both service READMEs and three of five workshop headers are wrong about what exists (framing §Drift). Debt not registered in the same PR evaporates: "the marker-interface / automation-shape skill debt is 'at threshold' per the handoff, but `DEBT.md` has zero open rows. The debt is real but unregistered" (state-of-the-repo 2026-06-25); the fix: "**A DEBT row blocked on code that does not exist yet is drained by the session that writes the code.**" (`implementations/009`).

The cadence rules worked and cost too much for one person. The no-opportunistic-edits rule needed a refinement: "*would this file still need touching if my change were reverted?* If no, it is in scope." (`implementations/009`). The observe-exercise-encode cadence "has earned its place as a default" (`docs/retrospectives/skill-template-namespaces-pattern.md`) yet the bundling rule "is at fourth confirmation" unencoded (`implementations/004`). Deleting one planning note "created 14 broken cross-references across 7 files" (`housekeeping-delete-may-15-handoff`). The narrative-skip session found that "the questions 'does this need a prompt?' and 'where does the retro live?' carried more deliberation than the design decision itself" (`telemetry-narrative-layer-decision`). Over the repo's life 8 of 44 merged PRs were implementation (18%), 16 were maintenance (36%), 11 design, 9 other; the last chain ran four consecutive implementation PRs with ADR-019 as the only interleave (`implementations/009`).

What v1 got right, in its own words: "The Event Model's GWT scenarios for slice 5.1 translated directly into the three integration tests." (`implementations/002`); "The prompt's instruction that `ReportLocationsHandler.cs` should not appear in the diff was met literally" (`implementations/008`); "If any pattern had been one-BC-only, the corresponding ADR would have been `Proposed` rather than `Accepted` — the discipline produced confidence, not just artifacts." (`decisions/002`); "There was no temptation to manufacture trivial edits to 'show work' — the verification record itself is the work." (`skills-tidy-ai-skills-sync`); "That is the thing the project exists to demonstrate, and it took four PRs of groundwork to make it a small session." (`implementations/009`).

## Risks of the recommendation

The boundary can be cosmetic: a tag and a vision bump are cheap and the apparatus can regrow; the only guards are the admission rule (nothing pinned, skilled or called committed without exercising code) and a smaller retro by default. The boundary session itself violates one-prompt-one-PR by design and touches the apphost and the Wolverine pin, both of which can break the Kafka and gRPC suites; run it as two PRs if the bump surfaces anything. Bobcat and CritterWatch 1.1 may not have shipped: the declared file and the renames do not wait on them, the binding and the aggregated picture do. CritterMart's Orders experiment may settle file conventions CritterCab would otherwise guess; authoring CritterCab's first file before it reports risks a second convention in the portfolio. Three infrastructure additions (SQL Server, Polecat, the ASB emulator with SQL Edge) arrive in one arc into a CI that already saturated Docker Hub once; sequence them as store, then transport, then slice, and enforce the pre-pull list first. The `polecat-*` skills are two majors stale. Freezing Onboarding strands the richest methodology content and the only DS-to-EM pair, and methodology log entry 005's second data point may never arrive in this repo. Five BCs makes CritterCab a thinner ride-sharing system than its name promises; readers wanting breadth will find it in the siblings. The ratio gets worse before it gets better: two or three more non-implementation PRs on a repo dormant since July whose lifetime ratio is 18% implementation. Deferring ASB, if the owner chooses that, reopens ADR-005, ADR-014 and ADR-018 and weakens the transport-per-flow-shape thesis; keeping it costs the emulator. The canvas changes the room, not the number of people in it; lean-confirmation remains a risk unless an outside practitioner reviews a chapter per arc.
